# 유튜브 레시피 뚝딱

유튜브 링크 하나에서 실제 사이트의 게시물까지 완성한다. 게시물 텍스트만 반환하거나 계획에서 멈추지 않는다. 사용자가 이미 정한 디자인·말투·계량 기준은 아래에서 적용하고 다시 선택을 요구하지 않는다.

글의 중심은 **영상의 레시피와 따라 하기 쉬운 조리 설명**이다. 시청자 댓글은 곁들이는 팁이나 재미 요소로만 활용한다. 댓글을 기준으로 제목·도입·구성·배합을 만들거나, 댓글 소재를 찾느라 집필을 지연하지 않는다. 선별·출처 표기 기준은 [references/editorial.md](references/editorial.md)를 따른다.

## 피드백 반영

사용자가 게시물에 피드백을 주면 현재 결과물을 수정하고, 다음 게시물에도 적용할 판단 기준을 관련 스킬 지침에 반영한다. 기존 규칙을 우선 수정·통합하며 충돌하는 지침과 오래된 예시를 함께 정리한다. 특정 글의 제목·도구 선택 같은 개별 결정은 그 글에만 남기고 보편 규칙으로 늘리지 않는다. 다음 생성 때 반영 여부를 확인하고, 수정한 스킬은 유효성 검사로 마무리한다.

## 작업 위치와 기준

- 기본 프로젝트: `/Users/shon/Desktop/benefit-finder` (IDE cwd의 groupby 저장소와 다름).
- 기본 도메인: `https://gibalpeople.com` (`gibelpeople` 아님).
- 이름: **레시피 나와라 뚝딱!**
- 소개: **유튜브에서 찾은 인기 레시피, 요리할 때 보기 편하게 담았어요.**
- 현재 김치찌개 게시물과 `BaseLayout.astro`, `global.css`를 실제 기준으로 먼저 읽는다. 이 스킬에 기록된 경로가 달라졌으면 현재 프로젝트 구조를 찾아 적응한다.
- 입력이 기존 영상이면 같은 영상을 새 글로 중복 발행하지 말고 기존 글을 갱신한다. 별도 버전 요청은 예외다.
- 링크만 있으면 그 영상을 사용한다. 다른 인기 영상으로 임의 교체하지 않는다. 조회수는 확인한 값과 날짜가 있을 때만 언급한다.

## 1. 원본에서 검증 가능한 레시피 확보

영상 페이지의 제목·채널·설명란·작성자의 고정 댓글과 접근 가능한 자막을 확인한다. 쇼츠는 설명란이 비어 있어도 고정 댓글에 전체 레시피가 있을 수 있다. 재생이 막혀도 일반 watch 페이지의 댓글은 로드될 수 있으므로 댓글까지 확인한 뒤 자료 부족을 판단한다. 작성자 댓글과 시청자 변형 레시피를 구분한다. 영상 ID는 watch, youtu.be, shorts 등 실제 URL에서 추출하고 임베드·썸네일·출처에 같은 ID를 쓴다.

원본의 재료·분량·인분·조리 순서·불 세기·시간을 기록하고 편집자의 환산/추가 팁과 구분한다. 원본 링크, 확인일, 근거가 설명란·작성자 댓글·자막 중 무엇인지, 근거 구간, 불확실한 내용을 `docs/recipes/<slug>-source.md`에 남긴다. 자막 전체를 재게시하지 않는다.

제목·썸네일·검색 미리보기만 확인하고 영상 내용을 본 것처럼 쓰지 않는다. 설명란이나 작성자 댓글에 레시피가 충분하면 이를 근거로 작성할 수 있다. 설명·작성자 댓글·자막 모두 부족하고 핵심 배합을 확인할 수 없으면 확인된 정보까지 보존하고 사용자에게 해당 설명이나 자막을 요청한다. 모델의 일반 요리 지식으로 원작자의 레시피를 꾸며 채우지 않는다.

## 2. 집필

[references/editorial.md](references/editorial.md)를 읽고 작성한다.

- 짧은 일상 도입 → 공식 영상 → 나란한 인분표 → 행동 중심 단계 → 해당 요리의 유용한 팁 → 출처 순서.
- 인분 선택 버튼 없이 **1–2인분 / 3–4인분**을 함께 표시.
- 재료는 그램보다 종이컵·밥숟가락·개·대·모·포기를 우선. 정확한 환산 근거가 없는 고형 재료의 부피를 만들어내지 않는다.
- 친근한 문장과 소량의 이모지/반응. 실제로 하지 않은 조리·시식 경험, 후기, 별점은 쓰지 않는다.
- 단계 수는 원본에 맞춘다. 김치찌개의 5단계나 물 보충 팁을 모든 요리에 강요하지 않는다.

## 3. 이미지 제작

[references/images.md](references/images.md)를 읽는다. 이미지 생성 시 사용 가능한 imagegen 스킬과 도구의 실제 사용 규칙을 따른다.

- 목록 썸네일: 사용자가 지정한 **해당 유튜브 영상 썸네일**. 출처 표시, 클릭 시 상세 글 이동.
- 본문 원본 영상: `youtube-nocookie.com` 공식 iframe과 원본 링크.
- 단계별 이미지: 직접 찍은 요리 사진을 수채화·연필로 옮긴 듯한 **자체 일러스트**. 제목의 실제 동작·크기·방향·재료 상태를 보여준다.
- 완성 이미지: 자체 일러스트. 상세 OG 및 Recipe 대표 이미지에도 사용.
- 감정 표현은 글의 맥락과 말투에 맞춘다([집필 기준](references/editorial.md)). 별도 감정 캐릭터는 요청받았을 때 제작한다. OGQ 스티커를 가져오는 것으로 해석하지 않는다.
- 이미지 생성 실패 시 다른 음식 그림이나 깨진 경로를 넣고 완료라고 하지 않는다. 원본 확인/텍스트 등 독립 작업을 진행하고 부족한 자산을 명시한다.

## 4. 실제 사이트에 연결

[references/site-integration.md](references/site-integration.md)를 읽는다. 기존 UI를 재디자인하지 않고 새 콘텐츠를 현재 패턴으로 연결한다.

1. 새 데이터, `/recipes/<slug>/` 상세, 이미지·출처 문서를 추가한다.
2. 홈 목록과 RSS에 새 글을 추가하고 기존 글을 보존한다. 목록과 RSS가 김치찌개 한 건에 하드코딩된 상태라면 복수 글을 지원하도록 최소한으로 확장한다.
3. 제목·설명·canonical·OG·Recipe JSON-LD를 해당 글의 값으로 설정한다. 구조화 데이터는 본문과 같은 재료·단계 데이터를 사용한다.
4. 사이트맵에 상세가 포함되는지 확인한다. 가짜 시간·평점·작성자·발행일은 추가하지 않는다.
5. 공통 애드센스 코드, 소유확인 파일, ads.txt, CNAME, robots와 기존 레시피를 보존한다.

## 5. 검증과 완료

- `npm run build` → `npm run verify:built`.
- `python3 <skill-dir>/scripts/audit_recipe.py --project /Users/shon/Desktop/benefit-finder --slug <slug>`.
- 390px와 1440px에서 목록 썸네일, 상세 이동, 이미지 표시, 재료표, 바로가기, 가로 넘침을 실제 브라우저로 확인. 재료표가 빽빽하면 320px도 확인한다.
- 모든 이미지의 실제 내용을 보고 본문과 다른 재료·순서·동작이 없는지 확인한다. 자동 검사는 그림의 정확성을 증명하지 않는다.
- 공식 리치 결과 테스트/검색 도구에 접근 가능하면 검증하고, 로컬 검증을 Google 승인이라고 표현하지 않는다.

기본 완료 범위는 **로컬 게시물 생성·목록/RSS 연결·검증**이다. 커밋/배포는 현재 대화의 사용자 승인 범위에 따라 수행한다. 이전 대화에서 배포했던 사실 자체를 새 세션의 포괄적 배포 허가로 해석하지 않는다. 이미 현재 세션에서 승인했다면 다시 묻지 않는다. 배포 시 기존 `scripts/deploy.sh`를 사용하고 완료 뒤 실제 공개 주소를 검증한다.

최종 답변에는 글 제목, 상세 경로, 원본 확인 범위, 이미지/검증 결과, 로컬 또는 공개 배포 여부를 짧게 알린다. 실제 조리처럼 사용자가 해야 하는 검증과 접근 불가능한 계정 작업만 남긴다.
